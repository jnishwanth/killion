# killion — code-quality audit

- **Date:** 2026-10-31
- **Audited tree:** `git HEAD fe68849` + uncommitted working-tree changes (working tree of 2026-10-31)
- **Scope:** `killion` (bash CLI), `watch.mjs`, `render.jq`, `selftest.jq`, `tiers.json`, `download_full.py`, `tests/` (run.sh, kb_battery.sh, kw_harness.mjs, kd_main.py, kd_parse.py, golden.sha), README.md, AGENTS.md, repo hygiene. Data files inspected for integrity (`full_dives.json` 35 MB / 106 dives / 742 questions / 431,649 answers; `party_answers.json` 112 entries).
- **Method:** full manual read of every source file; live run of the offline suite (`tests/run.sh` → **RESULT: PASS**, 25/25 golden cases); live `--selftest` (PASSED); targeted experiments (corrupt-party-file flush, room-close flush, fzf-less PATH, dataset scans); web checks for Node platform facts.
- **Environment:** macOS, bash 3.2, node v26.13.0, jq 1.7.1, fzf 0.74.5, python 3.15.2.

## Executive summary

The tool is in good shape: the architecture is simple and fits the AGENTS.md goals, the
invisibility requirement holds (watch never joins/acts — token endpoint + one anonymous room
stream only), lookups are fast (0.35 s measured), and the offline test suite is unusually
thorough for a personal tool (golden-hashed streams, pty-driven interactive cases, a
stubbed-WebSocket watcher driver, locale-proofed Python tests).

The dominant problem is **data integrity in the recording path** (`watch.mjs`): the
uncommitted 2026-10-30 recording session contains answers recorded under the *wrong
question* — at least 14 confirmed mis-pairings (English towns and shoe parts under
"Name a Spider-Man movie", "Croatia" under "Name a shade of blue", a "Highlighter" under
gymnastics apparatus). Because the *entire* currently-earned dataset is that session
(111 of 112 entries), this must be fixed before committing. Root cause: `record()`
attributes whatever it sees to the current `cat.text` with no round provenance, so a
player's stale `lastAnswer` (or a stale `pass` event) from a previous round lands under
the new question. The same bug also corrupts the live "already said" display, which can
hide a still-available answer mid-round.

Two data-loss paths in the same file were confirmed by experiment (room-closed exit
skips `flush()`; a corrupt `party_answers.json` is silently replaced by the next
flush). The rest of the findings are robustness/usability gaps of moderate or minor
severity: an undocumented Node ≥ 22 requirement, `watch`/`--selftest` needlessly
requiring fzf, non-atomic dataset writes, full re-download on every dataset refresh,
and a selftest that would miss tier re-assignment.

**Severity totals: 1 high · 7 medium · 17 low · 4 informational.**

## High

### H1 — Recording attributes answers to the wrong question (cross-round contamination) — `watch.mjs`

**Evidence (working tree, uncommitted `party_answers.json`, all firstSeen 2026-10-30):**

| question key | foreign answers recorded under it |
|---|---|
| `Name a Spider-Man movie` (20 entries) | `Stoke-on-Trent` (rare), `Worcester` (rare), `Bebington` (deepcut), `York` (schooler), `London` (plankton) — all verified answers to a UK-towns question; **and** `Aglet` (rare), `Toe box`, `Laces`, `Sole`, `Heel`, `Heel counter` (rare), `Outsole` (schooler) — all shoe parts. 12 entries, two different prior questions. |
| `Name a shade of blue` (14 entries) | `Croatia` (schooler) — a country. |
| `Name a piece of gymnastics apparatus` (9 entries) | `Highlighter` (schooler) — an office supply. |

The remaining 97 entries of the same session read semantically consistent; all 11 entries
from the single 2026-10-29 session are clean. A dataset-wide heuristic scan (party answer
that is daily-verified for a *different* question and not for its own) flags 77 entries —
all from 2026-10-30, the rest false positives from party-only questions that legitimately
overlap other questions' daily answers.

**Root cause.** `record()` (watch.mjs:134) keys everything on the *current* `cat?.text` at
call time. Two input channels can carry a previous round's answer into the new round:

1. **Stale `lastAnswer`** — `addSaidFromPlayer()` (watch.mjs:172) records
   `players[].lastAnswer` whenever it's new in `said`. If a new-round patch (or the
   reconnect snap) carries the players array before the server has cleared/updated
   `lastAnswer`, every player's previous-round answer is recorded under the new question.
   The two-round span (towns *and* shoe parts under Spider-Man) is consistent with a
   player who sat out a round still carrying the round-before-last answer.
2. **Stale `pass` events** — `applyEvents()` (watch.mjs:183) records every
   `{kind:"pass"}` in `snap.room.events` or `patch.events` under the current category.
   If the server ever batches a previous round's pass event with the new category, or
   replays a multi-round event log in the snap, the same contamination results.

Both vectors also poison the **live display**: the stale answer enters `said`, so the
viewer shows "already said" for an answer that is actually still available this round —
i.e. it can actively hide a good suggestion mid-round, which AGENTS.md names as the worst
outcome ("a wrong suggestion during a live round is worse than silence").

**Why it matters.** This is the one hard requirement the tool currently violates in
practice: what's shown is no longer "accepted and scored for *this* question". The
recorded dataset would feed wrong suggestions to the owner and to anyone replaying
`party_answers.json`.

**Recommendations**

1. **Repair the data before committing**: drop the 14 confirmed mis-paired entries
   (appendix A gives a ready-to-run jq command), and review the rest of the 2026-10-30
   session before trusting it.
2. **Fix the recording path** — require round provenance. Practical fix that works
   regardless of server patch ordering: at round start (snap and `newRound`), snapshot
   each player's current `lastAnswer` text as a *baseline* and never record the baseline
   value — only record `lastAnswer` **transitions** observed after the round started.
   `pass` events from a patch that does not change the category are fine as-is; for the
   snap, the log is assumed per-round (unverifiable offline — capture one raw snap/patch
   transcript in a future session to confirm server event scoping).
   Caveat to accept: if a player already answered in a round you join mid-way and the
   snap's event log does not include their pass event, the baseline fix would drop that
   sighting from the *record* (the said-display still shows it via the event log).
   Correctness over completeness is the right trade here.
3. **Add a validator** (e.g. `killion --check-party`): flag party entries whose answer is
   a daily-verified answer for a different question and not for its own — the heuristic in
   appendix A. It can't prove legitimacy, but it turns "trust me" into a reviewable list.

## Medium

### M1 — Room-closed exit skips `flush()`: recorded answers lost — `watch.mjs:225-226`

`ws.onclose` calls `process.exit(1)` for close codes 4404 ("room is gone") and 4403
("refused") without flushing. The SIGINT/SIGTERM handlers flush, and a new round flushes,
but the most common natural end of a session — the host closes the room — silently drops
every answer recorded since the last round boundary.

**Confirmed by experiment**: a stub harness feeding one accepted answer (`A1` under `Q
one`) then firing `onclose({code: 4404})` → process exits 1, `party_answers.json` still
`{}`.

Fix: `flush()` before `process.exit(1)` in both branches (flush is synchronous; safe to
call on the exit path).

### M2 — Corrupt `party_answers.json` is silently destroyed by the next flush — `watch.mjs:150-168`

`flush()` does `try { existing = JSON.parse(...) } catch {}` and proceeds with
`existing = {}` — i.e. an unparseable party file (a hand-edit mistake, a bad merge, a
truncated write from an old version) is **replaced** by only the new round's entries,
losing the entire earned record. The atomic tmp+rename protects against crash-mid-write,
not against already-corrupt input.

**Confirmed by experiment**: corrupt (bracket-unbalanced) pre-existing file + harness
run → post-flush file contains only the new entries; the pre-existing question is gone,
no warning printed.

Related: with a corrupt party file, `lookup()` fails its whole jq pass, so the watcher
shows "no game-verified answers yet (party-only category)" for *every* question — a
dataset-wide outage masked as an expected condition.

Fix: on parse failure, refuse to flush (back up the file as `party_answers.json.corrupt-<date>`
and keep buffering / print a loud error). A shape check (must be an object) would cover
valid-JSON-wrong-shape too.

### M3 — Undocumented Node ≥ 22 requirement — `watch.mjs`

`watch.mjs` relies on the global `WebSocket` (enabled by default only from Node 22 —
nodejs.org v22 release announcement) and the global WebCrypto `crypto` (default global
from Node 19). README lists "node" with no version. On Node ≤ 21 the watcher dies with a
raw `ReferenceError` at `connect()` (after the token fetch), and on ≤ 18 the
`crypto.getRandomValues` reference fails. The offline harness stubs both globals, so the
test suite passes on any Node and never catches this.

Fix: state `node ≥ 22` in README (or import `crypto` from `node:crypto` and add a
friendly `typeof WebSocket === 'undefined'` → "needs node ≥ 22" check, which also covers
future flag changes).

### M4 — `killion watch` and `--selftest` fail without fzf — `killion:38-43`

The top-level prerequisite check (`for cmd in fzf jq`) runs before mode dispatch, so on a
machine without fzf, `killion watch ABCD` dies with `error: fzf is required` even though
watch mode only needs node + jq. `--selftest` needs only jq (+ data files) and is also
held hostage by fzf. **Confirmed by experiment**: `PATH=/usr/bin:/bin ./killion watch
ABCD` → `error: fzf is required`, exit 1.

Fix: move the fzf check into the interactive branch (and jq into lookup/selftest/watch);
keep the data-file checks where they are.

### M5 — `download_full.py` writes outputs relative to CWD, reads `tiers.json` relative to the script — `download_full.py:26-27,140,143,157`

`open("full_dives.json", "w")`, `open("full_answers.csv", ...)`, `open("official_latest.json", ...)`
are CWD-relative, while `tiers.json` is read via `HERE`. Running `python3 download_full.py`
from any directory but the repo root silently writes the dataset somewhere else and leaves
the repo stale (and `--selftest`/lookup keep serving the old data). The offline test
(`kd_main.py`) masks this by chdir-ing into a scratch dir.

Fix: write all three outputs under `os.path.join(HERE, ...)` (or add a `--out` flag; the
tests already control CWD so HERE-relative keeps them green).

### M6 — Full re-download of every dive on every refresh — `download_full.py:110-127`

Every run fetches all 106 archive pages (2026-07-16 → latest) plus every roster file
(≈ 400–500 requests, several minutes), rewrites the 35 MB JSON, even though only the
latest dive is new. AGENTS.md explicitly says to "be a quiet client" toward shared
infrastructure. It also means a transient mid-run failure (3 retries per page, then the
dive is dropped) shrinks the dataset until the next full run succeeds.

Fix: incremental mode — if `full_dives.json` exists, keep existing entries for dates
older than (latest − small overlap window) and fetch only the new/overlapped days.
Cuts the daily run to ~10 requests and makes partial failures harmless.

### M7 — `--selftest` would miss tier re-assignment — `selftest.jq`

The selftest compares, per prompt, only **answer counts** (plus the full krillion-tier
list for the gem). If the mirror (or game) re-assigns an answer's tier within a prompt —
e.g. a schooler answer becomes a rare — every count still matches, the selftest passes,
and the tool would show the answer in the wrong tier (wrong suggestion, core requirement
#2). Tiers are the entire point of the ranking.

Fix: compare per-prompt tier histograms (or the sorted `(answer, tier)` multiset) — one
extra pass over the same data; the gem check stays. (Note the selftest by design can only
cover the *latest* dive, since the official API only serves that — worth a comment.)

## Low

### L1 — Clipboard strip is a string heuristic — `killion:103-105`

`answer_view` recovers the bare answer by cutting at the first `"  —"` (quip) or `"  (×"`
(seen-count) occurrence. If a real answer ever contains two spaces + em dash (or two
spaces + `×`), the copy is silently truncated. Current dataset: 0 daily and 0 party
answers match either pattern (8 daily answers contain an em dash, none with two leading
spaces), so this is latent. Structurally, render.jq knows the quip boundary but the text
protocol doesn't expose it; a control-character delimiter (like the existing `\x01`
convention) would make the copy exact.

### L2 — `killion --json` / `killion --all` with no question enters interactive mode — `killion:169-175`

With only flags and no query words, `rest` is empty, so on a TTY the tool starts the
interactive fzf loop and the flag is silently ignored (non-TTY gets usage). A flag-only
invocation probably deserves a usage error ("question required").

### L3 — Malformed WebSocket frame crashes the watcher — `watch.mjs:197`

`JSON.parse(String(e.data))` is unguarded in `onmessage`; one non-JSON frame (server bug,
proxy garbage) throws an uncaught exception and kills the process (after the last round
boundary, without flushing — compounds M1). A try/catch that drops the frame (and logs to
stderr) is a two-line fix.

### L4 — No clean error for missing/broken `tiers.json` or `jq` in watch mode — `watch.mjs:47-50,38-47`

- `readFileSync(TIERS_FILE)` at startup: missing/malformed tiers.json → raw stack trace.
- `lookup()` swallows all jq failures (`JSON.parse('')` → null): missing or broken `jq`
  makes every question report "no game-verified answers yet (party-only category)" — a
  tool-level failure masquerading as an expected condition (same masking as M2).
  One-shot and interactive modes at least print the jq stderr.

### L5 — Text mode silently drops answers with tiers missing from `tiers.json` — `render.jq` (daily branch)

The daily text/full branch only groups by `$order` tiers; an answer whose tier is not in
`tiers.json` is invisible in text mode but present in `--json`. The party-only branch has
an explicit "unscored" section for unknown/null tiers; the daily branch has no equivalent,
so the two branches are asymmetric. `watch.mjs` would show such answers under "unscored"
while the CLI hides them. Current dataset contains only the six known tiers, so latent —
but a new game tier would surface as *silently missing* in the CLI rather than
visible-but-miscategorized.

### L6 — If a question is ever re-asked in a later dive, the *first* (oldest) sheet wins — `render.jq`, `selftest.jq`

`$daily` is `[ ... | .[0] ]` over dives in date order, and `selftest.jq`'s count map keeps
the first-seen count. Today no question text repeats across the 106 dives (verified: 742
distinct), so this is dormant; if the game ever recycles a question with an expanded
answer list, the tool would show the older, smaller sheet and the selftest could false-
mismatch. Choosing the *latest* occurrence is the safer default.

### L7 — `mktemp` failure makes the interactive view cache un-invalidatable — `killion:86,118`

If `mktemp` fails, `VIEW_EPOCH=""`; `touch ""` then prints a usage error on every answer
view, and the epoch check (`[[ $VIEW_EPOCH && ... ]]`) is permanently false — a concurrent
`killion watch` recording new answers would go unnoticed for the whole session. Check the
mktemp result (fall back to no-caching rather than stale-caching).

### L8 — Quip association uses a 300-char lookahead that can cross into the next chip — `download_full.py:76-80`

For inline chips, the quip is the first `<span class="quip">` within 300 chars after the
chip's `data-copy` attribute. A chip *without* a quip whose *next* chip's quip lies within
300 chars would inherit the next chip's quip. The offline test can't catch this: the
fixture's expected output was recorded *by this same parser* (circular pin). A per-chip
segment (up to the next `data-copy` or `</details>`, whichever first) would close the gap.

### L9 — Last card's inline segment is hard-truncated at 60 KB — `download_full.py:57`

`end = ... else start + 60000` for the final card on the page. An inline-chip last card
with a roster bigger than ~60 KB would fail `got != tcount` and the whole dive is dropped
(as a "problem"). Bounded, and loud (the dive is reported), but the magic number deserves
a comment or a "to end of document" fallback.

### L10 — `download_full.py` retry semantics — `download_full.py:36-46,107-114`

- 404s are retried with 2 s + 4 s backoff like any other error. The latest-dive probe
  (up to 20 days back) can therefore burn ~2 minutes of pure sleeping when the archive is
  simply young/absent for those days. Distinguishing HTTP 404 (no retry) from 5xx/network
  (retry) would keep the probe tight.
- `python3 download_full.py --bogus` is silently ignored (`"--csv" in sys.argv[1:]`); a
  tiny arg validation would surface typos.

### L11 — `firstSeen`/`lastSeen` use the UTC date — `watch.mjs:132`

`new Date().toISOString().slice(0, 10)` is the UTC calendar day; in UTC+X timezones the
stamp is off by a day around local midnight. Labels only, no logic depends on them.

### L12 — New-round detection keys on `category.index` alone — `watch.mjs:210-217`

`said` is reset (and a flush fires) only when `s.category.index` differs. If the server
ever reuses an index with different question text, the previous round's "said" set (and
its stale-value exposure, see H1) would carry into the new round. The lookup itself is
text-based and would be fine. Comparing `index` **or** `text` change would be more robust.

### L13 — Non-atomic write of `full_dives.json` / `official_latest.json` — `download_full.py:140,157`

`json.dump` writes in place; a Ctrl-C or crash mid-dump leaves a truncated 35 MB file
that breaks every jq pass (lookup, selftest, qlist regeneration). The party file already
uses tmp+rename — apply the same convention to the dataset writes (the code comment at
that site shows the authors thought about mid-dump crashes but only fixed the encoding).

### L14 — `.gnhf/` agent-run logs are untracked and not gitignored — repo root

30 `.jsonl` agent-session logs under `.gnhf/runs/` (untracked; would show up in
`git status` if a new file lands there — directories with only untracked files are
hidden, so this currently sneaks by). Add to `.gitignore` (or delete) — session logs
don't belong in this repo and can contain more than the project cares to publish.

### L15 — Test suite is macOS-only — `tests/run.sh`, `tests/kb_battery.sh`

`script -q <file> <cmd>` (BSD script syntax), `shasum`, and `pbcopy` assumptions mean the
suite doesn't run on stock Linux. Fine for a personal macOS tool, but worth a one-line
note in the README/tests header so a future port doesn't chase a phantom failure.

### L16 — "said this round" line is uncapped — `watch.mjs:137`

The said-answers summary is one line with no cap; a 30-answer round wraps into a wall of
text on a small terminal. Cosmetic (the per-tier caps already bound the main list).

### L17 — Ambiguity listing has no cap — `render.jq` + `killion` `one_shot`

A query matching many questions (e.g. `killion "Name a"`) prints *every* candidate
question to stderr (hundreds of lines for broad prefixes). Useful, but a first-N lines +
"… and K more" cap would keep a fat-fingered query from flooding the terminal.

## Informational

1. **Invisibility holds.** `watch.mjs` performs exactly two network actions: one guest
   token fetch and one anonymous room stream (`key` random 128-bit per connection, token
   in query string). No join, no act, no presence. A fresh random key per reconnect
   correctly avoids the documented 4403 self-collision. Request volume is modest
   (one stream; reconnect at 1.5 s only while down).
2. **The offline suite is the project's strength.** Separate stdout/stderr golden hashes
   (pins stream discipline), pty-driven real-CLI copy tests with stubbed fzf/pbcopy,
   cache-invalidation tests that count jq invocations, a stubbed-WebSocket watcher driver
   that pins the reconnect-liveness bug, a fixture pinned against a real archived page,
   and a deliberate POSIX/C-locale re-run that pins explicit-utf-8 writes. `--regen`
   semantics are sane (refuses without the dataset).
3. **Single-pass jq design pays off.** One 35 MB pass ≈ 0.32–0.35 s (measured 0.35 s
   today); the qcache + per-question view cache make interactive re-Enter free, with
   mtime-precision epoch invalidation (bash `-nt` vs second-granular strings — a subtlety
   the comments handle correctly).
4. **Fail-closed posture is mostly right.** Selftest fails closed on malformed input
   (battery cases 20/24), the watcher degrades a network hiccup to retry, help works on
   a bare machine without creating files. The exceptions (masking failures as "no
   verified data" — M2/L4) are the ones to fix.
5. **Provenance note.** The dataset source is the krilliongame.net mirror; the official
   API only serves the latest completed dive, so dives older than that can never be
   cross-checked against the official source. The honest UA string and 0.25 s pacing are
   the right posture; M6 reduces the exposure further.
6. **Docs are in sync.** README/AGENTS.md match the code (modes, files, protocol facts,
   measured perf). The only doc gap found is the Node version (M3).

## Appendix B — suspect-scanning heuristic (for the recommended validator)

An entry `(question Q, answer A)` is flagged when `A` (case-folded) is a daily-verified
answer for at least one question other than `Q` and is **not** a daily-verified answer
for `Q`. It is a *review list*, not a verdict: party-only questions legitimately overlap
other questions' daily answers (that produced 63 of the 77 raw flags; semantic review
confirmed 14 true positives).

```sh
# step 1: daily answer (case-folded) -> questions it is verified for
jq '[.[] | .prompts[] | .q as $q | .answers[] | {a:(.a|ascii_downcase),q:$q}]
  | group_by(.a) | map({key:.[0].a, value:[.[].q]}) | from_entries' \
  full_dives.json > /tmp/daily_map.json

# step 2: flag entries (review list, not a verdict)
jq -r --slurpfile dm /tmp/daily_map.json '
  ($dm[0]) as $daily | to_entries[] | .key as $q | .value[]
  | select(($daily[.a|ascii_downcase] // []) as $qs | ($qs | index($q)) == null)
  | "\(.firstSeen)\t\($q)\t\(.a)\t\(.tier)"' party_answers.json
```

(Verified against the 2026-10-31 tree: 77 raw flags, all firstSeen 2026-10-30; the
cleanup command in appendix A verified on a copy — 112 → 98 entries, Spider-Man left
with exactly its 8 movie answers.)
