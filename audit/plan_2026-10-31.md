### T2 — stop the recorder attributing stale answers to the new question (H1, recommendation 2)

**Goal:** fix the root cause: `record()`/`addSaidFromPlayer()` in
`watch.mjs` attribute whatever they see to the current `cat?.text`, so a
players array whose `lastAnswer` still holds the previous round's value
(early new-round patch, or the reconnect snap) gets recorded under — and
displayed as "already said" in — the new round. That poisons both the
dataset and the live display (hiding still-available answers mid-round).
The fix must require round provenance from the state channel, per the audit's
recommendation (baseline at round start; only transitions count).

**Acceptance**
- A `lastAnswer` value present at round start (via **both** the snap path
  and the new-round-patch path) is neither recorded nor shown as said for
  the new question.
- A `lastAnswer` that *changes* after the round started is still recorded.
- `pass` events are still recorded unconditionally (per-round scoring
  record; existing semantics are pinned by the harness — a player who
  re-answers their baseline text is captured by their pass event, not by
  the state channel).
- The `tests/kw_harness.mjs` sequence is extended to prove all three, in the
  harness's existing style (scripted snap/patch, semantic assertions on the
  resulting party file). Existing harness facts must keep passing.
- The accepted tradeoff (mid-round join: a pre-join answer that isn't in
  the snap's event log is dropped from the *record*; correctness over
  completeness) is documented where the implementation lives.

**Notes**
- Per-player keying is the natural baseline shape (a global "seen texts"
  set would wrongly suppress Bob answering what Alice answered last round).
  Judgment left to the session — anything that passes the acceptance
  criteria is fine.
- `p.id` may be missing in theory; the real server sends ids and the
  harness does too — decide how much that edge is worth.
- Interacts with the accepted known issue in `milestones.md` ("reconnect
  double-counts `seen`"): a round-start baseline on the reconnect snap
  suppresses the *lastAnswer* half of that double-count; the event-log
  re-delivery half remains. T11 amends that entry — leave the watcher's
  behavior for the event half as-is (out of scope).
- New-round detection keys on `category.index` alone (audit L12, low):
  optionally harden while in there; default is to keep the diff focused.
- Whether the server ever batches a prior round's pass event with a new
  category is unverifiable offline (audit's own caveat) — the fix must be
  correct regardless; optionally capture one raw transcript in a later live
  session.

**Depends on:** T1 (clean data makes before/after comparison sane).

`onmessage` throws and kills the process (also unflushed). The audit
bundles these as watcher data-safety holes; both are tiny.

**Acceptance**

  everything recorded so far, including entries after the last new-round
  flush. Exit code stays 1 with the existing message.
- A harness variant proves it: an accepted answer landing after the final
  round boundary survives the 4404 exit (absent in the old code — a true
  regression pin).
- A non-JSON frame is dropped (logged to stderr is fine) and the watcher
  keeps running; a garbage frame in the main harness sequence must leave
  the golden output byte-identical (invisible when healthy).
- Existing harness facts + suite pass.

**Notes**
- `flush()` is synchronous — safe on the exit path. By the time T5 lands,
  a corrupt party file during this flush becomes backup + loud error, not a
  crash; don't build around the old behavior.
- 4403 is the same code path as 4404; one variant is enough, note the other.

**Depends on:** T2 (harness party-file state includes T2's entries).

### T5 — a corrupt `party_answers.json` must never be silently destroyed (M2)

**Goal:** `flush()` currently does `try { JSON.parse } catch {}` and
proceeds with `existing = {}` — an unparseable (or wrong-shape) party file
gets *replaced* by the new round's entries: the earned record, gone
silently. Related masking: with a corrupt file, `lookup()`'s jq pass fails
and every question reports "no game-verified answers yet" — a dataset-wide
outage disguised as an expected condition.

**Acceptance**
- On parse **or shape** failure (must be a JSON object), the corrupt file's
  bytes are preserved (audit's suggestion: rename to
  `party_answers.json.corrupt-<date>`; the exact mechanism is up to the
  session), a loud error goes to stderr naming what happened and where the
  data went, and the process does not crash.
- The audit's recommended behavior is "back up and keep buffering" — i.e.
  subsequent flushing continues to work. Note the tradeoff if choosing
  "refuse and keep failing loudly instead": buffered in-memory entries die
  at process exit (more data loss). Either is defensible; the silent-destroy
  status quo is not.
- A harness variant proves it: corrupt pre-seeded file + a normal run →
  exit 0, loud stderr, corrupt bytes preserved (recoverable content
  intact), recorded entries still land, and later flushes in the same
  session work normally.
- `.gitignore` covers any new local artifact this task creates.

**Notes**
- The masking half (lookup failing loudly instead of "no verified answers")
  is audit L4 (low, out of scope) — but the loud flush error already tells
  the owner the dataset is compromised; don't expand scope into fixing
  every jq-failure mask.
- The harness's corrupt-file variant needs its own copy dir (like the
  netfail variant) and semantic assertions — no golden line.

**Depends on:** T4 (same exit/flush paths, same harness surface).

### T8 — `download_full.py` must write into the repo, not the CWD (M5) + atomic writes (L13, audit-bundled)

**Goal:** the three outputs (`full_dives.json`, `full_answers.csv`,
`official_latest.json`) are written CWD-relative while `tiers.json` is read
script-relative — running from another directory silently writes the
dataset somewhere else and leaves the repo stale. Same three sites:
in-place `json.dump` means a Ctrl-C mid-dump leaves a truncated 35 MB file
that breaks every jq pass (audit L13, bundled — `watch.mjs` already uses
tmp+rename for the party file; apply the same convention).

**Acceptance**
- Outputs land next to the script regardless of CWD.
- Writes are atomic (or equally crash-safe); a killed run leaves either the
  old file or the new one, never a truncated one.
- The offline `kd_main.py` test proves it — and keep the explicit-utf-8
  guarantees the POSIX/C-locale re-run pins.

**Notes**
- The test currently *chdir*s into a scratch dir, which masks exactly this
  bug. Two obvious ways to unmask: an `--out`-style parameter, or stubbing
  `df.HERE` like the existing `df.get`/`df.date` stubs. The stub approach
  matches the file's existing test style and adds no CLI surface; a flag is
  also defensible. Pick one — whatever makes the test honest about "CWD ≠
  write target".
- `*.tmp` is already gitignored.

**Depends on:** nothing (but run before T9).

### T9 — stop re-downloading all 106 dives every refresh (M6) + L10 (audit-bundled)

**Goal:** every run re-fetches the full archive (≈400–500 requests, several
minutes) though only the latest dive is new — on a hobby mirror AGENTS.md
tells us to be quiet — and a transient mid-run failure *shrinks* the
dataset until the next full success. Bunched by the audit: HTTP 404s are
retried with backoff (the latest-dive probe can burn ~2 min of pure
sleeping), and `--bogus` is silently ignored.

**Acceptance**
- With an existing valid `full_dives.json`, a normal run fetches only the
  new/overlap days (a few pages, not 106) and rewrites the dataset as
  existing entries + fresh window.
- A fetch failure inside the window for a date that already exists keeps
  the existing entry (loudly noted) — partial failure no longer shrinks
  the dataset. A failure for a genuinely new date is reported as a problem
  (today's semantics).
- An escape hatch forces the full re-download (name up to the session;
  `--full` is the obvious one), and unknown flags are rejected instead of
  ignored.
- 404s are terminal in `get()` (no retry/backoff); 5xx/network still
  retry. The probe against a young archive is quick.
- `kd_main.py` grows offline cases proving: old dates untouched (and — the
  core assertion — never even *requested*), window fetched, in-window
  failure harmless, and the full-mode escape hatch. The existing cases
  (default run, `--csv`, doctored-official MISMATCH) keep passing.
- The mirror gets the "quiet client" treatment: one honest UA, existing
  pacing, ~10–25 requests on a normal day.

**Notes**
- The audit's shape: keep existing entries for dates older than
  (latest − small overlap window); the overlap exists to pick up mirror
  revisions of recent pages. Size of the window is a judgment call
  (2 days is the audit's implicit suggestion).
- Date-keyed merging also means hand-added/hand-edited entries survive;
  decide (and note) what happens if the existing file has a date *newer*
  than the probe's latest, and if the existing file is corrupt (full
  rebuild + note is the sane answer).
- Dive numbers: the existing formula is `n = days-from-START + 1`
  (START = 2026-07-16, dive #1; the test fixture is 2026-08-31 = DIV47).
  Don't renumber kept entries.
- A live `python3 download_full.py` after the change should print ~3 dive
  lines, not 106 — a reasonable manual check (read-only against the
  mirror; owner's call whether to run it).

**Depends on:** T8.

**Acceptance**

- A battery case with a doctored official file (one answer's tier changed,
  counts unchanged, gem untouched) now reports MISMATCH and exits 1; the

- The gem check stays. A comment notes what the selftest can and can't
  cover (official API serves only the latest dive — per the audit; also
  note the shared first-occurrence prompt semantics if audit L6 is ever

- Golden diff reviewed: new case line + the selftest cases whose output
  gains the new rows.

**Notes**
- The doctoring case must change a tier *off* the gem's prompt (the gem
  reads the first official prompt) and off any tier it already is (check
  the real `official_latest.json` value before fixing the case) — a
  same-tier or gem-affecting doctoring would muddy what the case proves.
- Expect the doctored case to mismatch on *two* tiers (source and target)
